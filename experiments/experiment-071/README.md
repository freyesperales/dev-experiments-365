## Why it exists

VRAM calculators make you *pick a model by hand* and apply generic formulas. The real answer is already inside the file: every tensor's exact type and size, the layer count, the KV-head count, and the chat template. gguf-xray reads those, so it knows e.g. that *this* quant mix puts 4.2 GB in weights, that *this* model uses GQA (8 of 32 KV heads) and so needs a quarter of the KV cache a naive formula predicts, and exactly how many layers to pass to `-ngl` when it only half fits.

It also catches the quiet failures people hit after the download: templates that print `bos_token` while the tokenizer *also* adds one (double BOS), reverse slices (`[::-1]`) that older llama.cpp can't parse, tool templates that need `--jinja`, a missing EOS token, a requested context beyond what the model was trained for, and **truncated downloads** (the tensor table says the file should be N bytes; it isn't).

## What it checks

| Area | Details |
|---|---|
| Header | GGUF v2/v3, all value types, huge tokenizer arrays skipped without being stored, adaptive read window |
| Weights | Exact bytes per tensor from ggml block layouts (F32…Q8_0, K-quants, IQ-quants, BF16), per-quant share, bits/weight |
| KV cache | layers × KV heads × (K+V dim) × context × element size; f16 / q8_0 / q4_0; per-layer KV-head arrays |
| Fit | Full offload, partial offload (max `-ngl` that fits), CPU-only, or no fit given your RAM; max context for full offload |
| Template/file | double BOS, reverse slice, `strftime_now`, tools/`--jinja`, reasoning templates, no template, no EOS, ctx over trained, split shards, truncation |

## Limitations (honest)

- **Estimates, not guarantees.** Compute buffers are a flat, editable 512 MB; real overhead varies with batch size, backend (CUDA/Metal/Vulkan) and flash-attention.
- KV sizing assumes classic attention. MLA models (DeepSeek-style) are **overstated**; sliding-window layers are **overstated**. Both are flagged when detected.
- Partial offload assumes layers are roughly equal in size, and ignores multi-GPU splits and `--override-tensor` MoE tricks.
- Template checks are text heuristics, not a Jinja renderer; they catch known pitfalls, not all of them.
- Only the header is read, so tensor *data* corruption is not detected (only truncation).
- The test fixtures are synthetic but spec-accurate GGUFs built in the test suite; no multi-GB real model was available offline in this run. Big-endian and GGUF v1 files are rejected with a clear message.
